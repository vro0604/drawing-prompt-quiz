雑務を洗い出して、そのまま直してください。一覧を出して止まるのではなく、
調査から修正まで通してやってください。

## 1. 準備

- git リポジトリなら `git status --short` を実行する。未コミットの変更が
  あれば、その件数を1行報告してから進む。止まらない。
- 確認手段（テスト、型チェック、起動コマンド）が何かを、CLAUDE.md か
  package.json か同等の設定ファイルから1つ探す。見つからなければ
  「確認手段なし。目視のみ」と1行書いて進む。
- 作業ディレクトリ直下（git リポジトリならリポジトリ直下）の BACKLOG.md が
  あれば読む。既に積まれている項目を把握しておく。無ければ後で作る。

## 2. 調査

範囲全体を Grep と Glob で絞ってから、一致箇所の周辺だけを読む。
全文を読まない。次のものを探す。

- 実際に動作がおかしくなるバグ。条件の取り違え、境界の扱い漏れ、
  戻り値の見落とし
- エラーが起きたときに何も起きない箇所。握りつぶし、握り漏れ
- 到達しないコード、呼ばれていない処理、消し忘れ
- 表示の不具合。誤字、文言の不統一、桁や単位のずれ
- 同じ値が複数箇所に書かれていて食い違っているもの
- コメントや説明と、実装が食い違っているもの
- TODO / FIXME / HACK と書かれたまま放置されているもの
- 明らかに無駄な繰り返し、同じ処理の重複

## 3. 仕分け

見つけたものを、雑務とそれ以外に分ける。

雑務 — 次の3つを全部満たすもの。
- 直しても、画面の構成や操作の流れが変わらない
- 直しても、他の場所を連鎖して直す必要がない
- 機能が増えない（既にあるものが正しく動くようになるだけ）

雑務でないもの — 1つでも当てはまれば、こちら。
- 新しい機能を足す、または重要な機能の挙動を変える
- 画面の構成や操作の流れを作り変える
- データの持ち方、保存の形式を変える
- 複数ファイルにまたがる連鎖修正が要る
- 外部への公開、お金、認証情報が絡む

判断に迷ったものは、雑務でない側に入れる。

## 4. 雑務でないものを BACKLOG.md に書く

修正を始める前に、雑務でないと仕分けたものを全部 BACKLOG.md に書き出す。
後で着手できる形にすることが目的なので、読んだだけで作業を始められる
だけの情報を書く。「〜を検討」で終わらせない。

ファイルが無ければ、次の書き出しを付けて新規作成する。

```
# BACKLOG

着手前の項目を置く場所です。/chores が「雑務でない」と仕分けたものが
ここに積まれます。着手して直したら、その項目を削除してください。
やったことの記録は PROGRESS.md の「終えたこと」に残ります。
```

項目は下の形で、ファイルの末尾に足す。番号は既存の最大値の続きにする。

```
## B-007 （何が問題かを1行で。解決策ではなく症状を書く）
- 見つかった日: YYYY-MM-DD
- 場所: path/to/file.ext:123 （複数あれば全部）
- 現状: 今どうなっているか。動かしたときに何が起きるか
- なぜ雑務でないか: 仕分けの5条件のどれに当たったか。1行
- 直すとどうなるか: 着手する価値。動作の変化で書く
- 着手前に決めること: 判断が要る点。無ければ「なし」
- 影響範囲: 直したときに巻き込まれる場所。分かる範囲で
```

同じ場所の同じ問題が既に BACKLOG.md にあれば、新しい項目を足さない。
既存項目の「見つかった日」の行に、今日の日付を追記する（再検出の記録）。

## 5. 着手前の報告

修正を始める前に、次の2つを出す。ここで止まらない。出したら続けて直す。

- 「雑務: N 件。これから全部直します」と1行。続けて番号付きで、
  1行ずつ「何を直すか — どのファイルか」。
- 「BACKLOG に追加: M 件（既存 K 件）」と1行。続けて、追加した項目の
  番号とタイトルだけを1行ずつ。詳細は繰り返さない。ファイルにある。

## 6. 修正

- 危険度の低いものから順にやる。表示や誤字の修正を先、動作に関わる修正を後。
  途中で止まったときの被害を小さくするため。
- 1件直すごとに、準備で見つけた確認手段を実行する。通ってから次へ進む。
  確認手段が無い場合は、変更箇所を読み返して意図どおりか見る。
- 1件が詰まったら、そこで止まらず飛ばして次へ進む。飛ばしたことは記録する。
- BACKLOG.md に入れたものには、一切手を出さない。
- 途中で私に確認を取らない。全部やり切る。
- 応答の残量が尽きそうになったら、そこまでを報告し、残りを PROGRESS.md の
  「次の一手」に書いて終える。黙って打ち切らない。

## 7. 報告

全部終わったら、散文で次を書く。関数名の羅列にしない。

- 何ができるようになったか。動作の変化を、コードを見ていない人に通じる言葉で。
- 何を引き換えにしたか。無ければ「引き換えは無し」と明記する。
- 飛ばした項目と、その理由。
- BACKLOG.md に積んだ件数と、その中で最も影響が大きいと思うものを1つ。
  理由を1行付ける。

そのあと PROGRESS.md に、終えたこと・次の一手・触ったファイルを追記する。
BACKLOG.md に項目を足した場合は、「次の一手」にその件数を書く。

## 引数

「$ARGUMENTS」に範囲（ディレクトリ名など）や種類（「表示のずれ」など）が
書かれていれば、そこに絞って調査する。空なら範囲全体を対象にする。

## 守ること

- 件数が多くても打ち切らない。上限を自分で決めない。
- 「これは直す価値が無い」と自分で判断して落とさない。雑務なら直す。
  雑務でないなら BACKLOG.md に積む。どちらでもなく捨てる、をしない。
- コミットもプッシュもしない。変更を作業ツリーに置いたままにする。
- 自分が直したものを「問題なし」と断定しない。確認手段を通した事実だけ書く。
