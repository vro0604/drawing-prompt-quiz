# 2026-09-08 絵1枚を、どれだけの箱に、どう収めているか

今日調べたのは、絵や写真を並べて見せる実在のサービスと決まりごとが、1枚の絵を
どんな大きさの箱に入れ、箱に入りきらないときに切り取るのか、縮めるのか、
それとも箱のほうを絵に合わせるのかを、どの数値で決めているか。

これを選んだ理由は、既存の調査3本（主色の決め方、当たり外れの見せ方、
絵を見せたまま選択肢を出す画面の組み方）がどれも色と配置までで、
絵そのものの寸法をどう扱うかを一度も見ていないため。このサービスは絵だけを
手がかりにお題を当てる仕組みなので、絵の何割が見えているかは飾りではなく機能にあたる。

## 先に断っておくこと（読めた範囲）

見ていないものを見たことにしないために、今日の環境で何が読めて何が読めなかったかを先に書く。

- ページを開いて中身を読む道具（WebFetch）は、試した宛先がどちらも遮断された。
  実際に試したのは design-system.service.gov.uk と www.w3.org の2件で、
  どちらも組織の通信方針による拒否（EGRESS_BLOCKED）だった。迂回はしていない。
  よって、この報告に出てくる URL のうち、ウェブページとして開いたものは1つも無い。
- 検索は通った。ただし検索が返した日本語の記事は、どれも一般論の解説で、
  数値の出所がたどれなかった。今日の事例には1件も採っていない。
- 公開リポジトリ（配布元の置き場）の複製は通った。下の8件はすべて、複製して
  原本のファイルを直接読んだもの。読んだ版が後から動かないよう、
  各事例に commit（その時点の版を指す番号）と日付を書く。
- 画像は1枚も見ていない。見た目の印象は書かず、数値と原本の記述だけで書く。

## いまの実装の実測（このリポジトリを読んで計算した）

事例の前に、比べる相手をはっきりさせておく。以下は src/app の中身を読んで、
CSS の指定から計算した値で、どこかから引いてきたものではない。

一覧（/works）のカード1枚。

- 外枠は `max-w-5xl`（1024px）で、左右の余白が `p-6`（24px）、
  広い画面では `sm:p-10`（40px）。
- 並べ方は `grid gap-5 sm:grid-cols-2 lg:grid-cols-3`。列の間は 20px。
- カードは `border`（1px）と `p-3`（12px）を持つ。
- 絵の箱は `h-48 w-full object-cover`。**高さが 192px に固定されていて、
  はみ出した部分は切り取られる。**

ここから、絵の箱の実際の大きさは次のようになる。

| 画面の幅 | 列の数 | 絵の箱の幅 | 絵の箱の高さ | 箱の形（横÷縦） |
|---|---|---|---|---|
| 1024px 以上 | 3 | 275px | 192px | 1.43（横長） |
| 640px | 2 | 244px | 192px | 1.27（横長） |
| 390px（携帯） | 1 | 316px | 192px | 1.65（横長） |

投稿できる絵に縦横比の制限は無い（src/features/work/types.ts にあるのは
容量の上限 5MB だけ）。つまり、縦長の絵は必ず横長の箱に入ることになる。
`object-cover` は箱を埋めるまで拡大してから、はみ出しを切る。
1024px 以上の画面（箱 275×192）で、絵の何割が消えるかを計算すると次のとおり。

| 絵の形 | 箱に入れたあとの大きさ | 見えている割合 | 消える割合 |
|---|---|---|---|
| 正方形 1:1 | 275×275 | 高さの 69.7% | 30.3% |
| 縦長 3:4 | 275×367 | 高さの 52.3% | 47.7% |
| 縦長 2:3 | 275×413 | 高さの 46.5% | 53.5% |
| 横長 4:3 | 275×207 | 高さの 93.0% | 7.0% |
| 横長 16:9 | 341×192 | 幅の 80.7% | 19.3% |

縦長の絵は、半分ほどが一覧に出ていない。しかも切り取られるのは上下の端なので、
絵の中心にしか手がかりが無い場合はまだしも、端に描かれたものは一覧では見えない。

作品ページ（/works/[id]）は逆側に振れている。絵は `h-auto w-full` で、
外枠は `max-w-3xl`（768px）。縦横比はそのまま保たれるかわりに、**高さの上限が無い。**
携帯（幅 390px、左右 24px）で 2:3 の縦長の絵を開くと、絵だけで 513px の高さになる。
携帯の画面の高さは 650px から 850px ほどなので、絵の下にある選択肢は画面の外にある。
これは PR #8（2026-09-04 の調査）が別の道筋で見つけた問題と同じ場所に出ている。

## 事例

### 1. object-fit の定義（MDN の原文）

- 出所: https://github.com/mdn/content/blob/main/files/en-us/web/css/reference/properties/object-fit/index.md
  （mdn/content を複製して読んだ。commit 44eeecc 、2026-09-07）
- 何をしているか: 絵を箱に収める方法として5つの値を定義している。`cover` は
  「縦横比を保ったまま箱いっぱいに広げ、比が合わなければ切り取る（clipped）」。
  `contain` は「縦横比を保ったまま箱の中に収め、比が合わなければ上下または左右に
  余白が出る（letterboxed / pillarboxed）」。`scale-down` は「`none` と `contain` の
  うち、結果が小さくなるほうと同じ」で、小さい絵を引き伸ばさない。
- なぜそうしていると思われるか: 推測ではなく定義そのもの。ここで確かめたかったのは
  「cover は切る、contain は余白が出る」が本当に規格の言葉で書かれているかで、書かれていた。
- 当てはめるとどうなるか: いまの一覧は `cover` なので、切り取りは設定の副作用ではなく
  指定どおりの動作である。切りたくないなら `contain` に替えるだけで足りる。
  投稿された絵が箱より小さいときに引き伸ばしたくないなら `scale-down` がある。
- 当てはめない方がよい理由: `contain` は余白を生む。余白の色を決めないまま替えると、
  絵の白い地と画面の地の境目が分からなくなる（下の判断が要る点 C）。

### 2. Discourse（掲示板）— 箱に収めるのが既定、切るのは例外

- 出所: https://github.com/discourse/discourse/blob/main/lib/image_sizer.rb
  および config/site_settings.yml
  （discourse/discourse を複製して読んだ。commit d82756af 、2026-09-08）
- 何をしているか: 投稿の中の画像は `max_image_width: 690` と `max_image_height: 500` の
  箱に収まるまで縮小される。`ImageSizer.resize` は横と縦それぞれの縮小率を出して
  小さいほうを採る作りで、切り取りは起きない。切り取る道（`ImageSizer.crop`）も
  あるが、使われるのは `min_ratio_to_crop`（既定 0.22）より細長い画像だけ。
  横÷縦が 0.22 ということは、縦が横の4.5倍以上ある画像を指す。
- なぜそうしていると思われるか: 掲示板は文章の流れの中に画像が挟まる。1枚が縦に
  伸びると後ろの投稿が読めなくなるので、上限を置く必要がある。一方で内容としての
  画像を勝手に切ると意味が変わるので、切るのは「文章として成立しないほど細長い」
  場合だけに絞った、と読める。
- 当てはめるとどうなるか: 一覧の箱を「高さ 192px 固定」から「縦横それぞれの上限」に
  変えると、この型になる。切り取りをやめても、極端に細長い絵だけは別扱いにできる。
- 当てはめない方がよい理由: この型ではカードの高さが絵ごとにばらつく。
  いまの3列の並びだと、行ごとに段差ができる。

### 3. Lemmy（掲示板）— 一覧は小さな正方形、開いた先は画面の高さで止める

- 出所: https://github.com/LemmyNet/lemmy-ui/blob/main/src/assets/css/main.css
  （LemmyNet/lemmy-ui を複製して読んだ。commit c277a8a 、2026-09-01）
- 何をしているか: 一覧の縮小画像は `.thumbnail { height: 80px; width: 80px;
  object-fit: cover; aspect-ratio: 1/1 }`。正方形に切り取る。ただし携帯向けの
  入れ物の中では `.mobile-thumbnail-container .thumbnail { width: 100%; height: auto }` に
  上書きされ、切り取りをやめて幅いっぱいに出す。開いた画像は
  `.img-expanded { max-height: 90vh }`、本文中の画像は `.md-div img { max-height: 40vh }`。
  vh は画面の高さの1パーセントを表す単位。
- なぜそうしていると思われるか: 一覧では画像は「どの話題か」を見分ける印であって
  中身ではないので、小さく切ってよい。画面が狭いと 80px の印は役に立たないので、
  そこでは切り取りをやめる。開いた先では中身を見せる必要があるが、画面より高いと
  操作できなくなるので、画面の高さの9割で止める。役割ごとに扱いを変えている。
- 当てはめるとどうなるか: 作品ページの絵に `max-height` を入れる根拠になる。
  数値の前例が2つあり、主役として見せる場合が 90vh 、文章に挟まる場合が 40vh 。
- 当てはめない方がよい理由: このサービスの一覧の絵は「どれか見分ける印」ではなく
  中身そのものなので、80px の正方形に切る側はそのまま借りられない。

### 4. Mastodon（投稿と閲覧が混ざるサービス）— 1枚なら絵の形に箱を合わせる

- 出所: https://github.com/mastodon/mastodon/blob/main/app/javascript/mastodon/components/media_gallery.jsx
  および app/models/media_attachment.rb
  （mastodon/mastodon を複製して読んだ。commit a6d857a 、2026-09-07）
- 何をしているか: 添付が1枚のときは `style.aspectRatio` にその画像自身の縦横比を入れ、
  箱のほうを絵に合わせる。2枚以上のときだけ `3 / 2` の固定の箱にして、
  中身は CSS の `object-fit: cover` で切り取る。サーバー側の縮小は
  `small: { pixels: 230_400 }`（640×360 に相当する画素数）という**面積**の指定で、
  縦横のどちらかを固定してはいない。
- なぜそうしていると思われるか: 1枚しか無いなら並びを揃える相手が居ないので、
  切る理由が無い。複数を並べるときだけ、格子を作るために形を揃える必要が出る。
  縮小を面積で指定しているのは、縦長でも横長でも同じ重さになるようにするため、と読める。
- 当てはめるとどうなるか: 「揃えるために切る」のであって「切ってから揃える」のではない、
  という順番がはっきりする。一覧は複数を並べる場所なので揃える理由はあるが、
  作品ページは1枚なので、絵の形をそのまま使うのが筋になる（いまもそうなっている）。
- 当てはめない方がよい理由: 面積で縮小する仕組みは画像の変換をサーバーで行う前提で、
  このサービスは投稿された画像をそのまま置いている。取り入れるなら変換の工程が要る。

### 5. Flickr の justified-layout（絵を切らずに敷き詰める）

- 出所: https://github.com/flickr/justified-layout/blob/master/lib/index.js
  （flickr/justified-layout を複製して読んだ。commit 9d4db49 、2021-01-06）
- 何をしているか: 縦横比の一覧を渡すと、各行の高さを揃えたまま、幅で辻褄を合わせた
  座標を返す。既定値は目標の行の高さ 320px 、許容 0.25（目標から上下25%まで動かす）、
  絵の間 10px 、外枠の余白 10px 。行の高さは最低でも目標の 0.5倍、最高でも 2倍に
  抑える（`edgeCaseMinRowHeight` と `edgeCaseMaxRowHeight`）。1枚も切り取らない。
- なぜそうしていると思われるか: 写真の共有サービスなので、切り取りは作者の構図を
  壊す行為になる。そこで「切らない」を守り、そのかわり行の高さを少し動かして
  端を揃えている。読んだのは実装だけで、この理由が書かれた文書は見ていない。推測。
- 当てはめるとどうなるか: 3列の格子をやめて、行ごとに枚数が変わる並べ方にすれば、
  絵を1ミリも切らずに端を揃えられる。縦長の絵は細く、横長の絵は広く出る。
- 当てはめない方がよい理由: カードに題名と作者名を載せているので、
  絵の幅が絵ごとに変わると、文字の入る幅も変わる。細い絵のカードでは題名が
  ほとんど読めなくなる。この並べ方は絵だけを並べる画面に向いている。

### 6. Immich（同じ考え方の、いまの実装値）

- 出所: https://github.com/immich-app/immich/blob/main/web/src/lib/components/shared-components/gallery-viewer/GalleryViewer.svelte
  および web/src/lib/utils/layout-utils.ts
  （immich-app/immich を複製して読んだ。commit 58fb1ed 、2026-09-07）
- 何をしているか: 上と同じ「行の高さを揃える」並べ方を使っていて、渡している値が
  `heightTolerance: 0.5` と `rowHeight: Math.floor(viewport.width) < 850 ? 100 : 235` 。
  画面の幅が 850px 未満のときは行の高さを 100px 、それ以上では 235px にする。
  並べる材料は縦横比の配列（`aspectRatios`）だけで、画素の寸法は渡していない。
- なぜそうしていると思われるか: 狭い画面では1行に入る枚数が減るので、行を低くして
  枚数を保っている、と読める。許容を 0.5 と大きく取っているのは、
  写真の縦横比がばらつくため。実装値からの推測で、理由の文書は見ていない。
- 当てはめるとどうなるか: 行の高さの現実的な数値がここにある。狭い画面で 100px 、
  広い画面で 235px 。いまの固定 192px は、広い画面向けの値としては小さめということになる。
- 当てはめない方がよい理由: 事例5と同じ。文字を載せるカードには向かない。

### 7. Bootstrap のカードと縦横比の道具（高さを決めない側の前例）

- 出所: https://github.com/twbs/bootstrap/blob/main/scss/_card.scss
  および scss/helpers/_ratio.scss 、scss/_variables.scss
  （twbs/bootstrap を複製して読んだ。commit 12cb8b9 、2026-09-01）
- 何をしているか: カードの画像 `.card-img-top` に入っている指定は `width: 100%` と
  角の丸みだけで、**高さも object-fit も無い。**絵の縦横比はそのまま出る。
  形を揃えたいときは別の道具 `.ratio` を被せる作りで、用意されている比は
  `1x1`（100%）、`4x3`、`16x9`、`21x9` の4つ。中身は入れ物いっぱいに広げられる。
- なぜそうしていると思われるか: 部品の側で高さを決めてしまうと、決めた比が合わない
  使い方のときに直せない。既定は何もせず、揃えたい人だけが比を指定する、
  という切り分けだと読める。
- 当てはめるとどうなるか: 「箱の比を1つ決める」を選ぶ場合、決め打ちできる比の候補が
  ここにある。とくに `1x1`（正方形）は、縦長と横長のどちらも大きく損なわない比になる。
- 当てはめない方がよい理由: 無し。ここは考え方だけを借りる話で、
  このリポジトリは Bootstrap を使っていない。

### 8. Excalidraw の書き出し余白（絵の周りに必ず余白を置く）

- 出所: https://github.com/excalidraw/excalidraw/blob/master/packages/common/src/constants.ts
  および packages/excalidraw/scene/export.ts
  （excalidraw/excalidraw を複製して読んだ。commit 0361bdd 、2026-09-07）
- 何をしているか: 絵を画像として書き出すとき、`DEFAULT_EXPORT_PADDING = 10`（px）を
  絵の外周に足す。描かれたものを囲む最小の矩形を求め、その四方に 10px を加えた
  大きさで画布を作る。ただし枠（frame）を書き出すときだけは `exportPadding = 0` にして、
  枠の線をそのまま端にする。
- なぜそうしていると思われるか: 線が画像の端に接していると、切れているように見える。
  枠を書き出す場合は枠の線が端であることに意味があるので余白を消す。
  絵と枠で扱いを分けているところから、そう読める。推測。
- 当てはめるとどうなるか: 作品ページの絵には `border border-line` が直接付いている。
  絵の内容が端まで描かれている場合、線と絵が接する。あいだに数 px の余白を置くか、
  枠を絵から離すかで、絵の端が絵の一部なのか枠なのかがはっきりする。
- 当てはめない方がよい理由: 投稿された画像にはすでに作者が付けた余白が入っていることが
  多い。こちらでも足すと、余白が二重になって絵が小さく見える。

## 読み取れること

- 8件のうち、絵を切り取ることを既定にしているのは1件（Lemmy の一覧の 80px の印）だけで、
  それも「どの話題か見分ける印」という役割の場合に限られている。
  中身として見せる場面では、7件とも切らずに縮める側に寄せている。
- 切るか切らないかの分かれ目は、絵の役割で決まっている。並びを揃える必要があるか、
  絵そのものが情報かの2点。このサービスの一覧の絵は、並びを揃えたい場所に置かれた
  情報そのもの、という両方に当てはまる珍しい場合になる。
- 高さの上限は、切り取りとは別の道具として使われている。Discourse は 500px 、
  Lemmy は 90vh と 40vh 。どれも「絵が縦に伸びて後ろが読めなくなる」ことへの対処で、
  絵の中身は削っていない。作品ページに足りていないのはこちらである。
- 「箱の形を先に決めて絵を合わせる」（Bootstrap の ratio 、Mastodon の複数枚）と
  「絵の形に合わせて箱を作る」（Mastodon の1枚、Flickr 、Immich）の2つがあり、
  どちらを選ぶかで並びの揃い方と文字の置き場所が決まる。

## 判断が要る点

### A. 一覧のカードで、絵を切り取るのをやめるか

- 決めること: いまの「高さ 192px 固定・はみ出しは切る」を続けるか、変えるか。
- 選択肢:
  - (a) いまのまま。縦長の絵は半分ほどが一覧に出ない。
  - (b) 箱を正方形にして、絵の全体を入れる（`object-contain`）。
    1024px 以上の画面で箱は 275×275 になり、2:3 の縦長は 183×275 、
    4:3 の横長は 275×206 で、どちらも全部見える。カードは 83px 高くなる。
  - (c) 箱を正方形にしたうえで、いまどおり切り取る（`object-cover`）。
    切り取られる量は、2:3 の縦長で 53.5% から 33.3% に減る。全部は見えない。
  - (d) 箱の高さを決めず、絵の縦横比のまま並べる。1枚も切れないが、
    カードの高さがそろわず、行ごとに段差が出る。
- 推奨: (b)。このサービスは絵だけが手がかりなので、一覧で半分が消えていると、
  どれを開くかの判断そのものが歪む。正方形にするのは、縦長と横長のどちらにも
  最悪の結果を出さない比だから（事例7）。カードの高さは揃うので並びは崩れない。
  余白が出る側の色は C で決める。
- 答え方: 「絵の収め方: a」「絵の収め方: b」「絵の収め方: c」「絵の収め方: d」

### B. 作品ページの絵に、高さの上限を付けるか

- 決めること: いまは上限が無い。携帯で縦長の絵を開くと、絵だけで画面の6割から8割を
  占め、選択肢が画面の外に出る。
- 選択肢:
  - (a) 付けない。
  - (b) 画面の高さの何割かで止める。前例は Lemmy の 90vh（主役として見せる場合）と
    40vh（文章に挟まる場合）、Discourse の 500px 。
  - (c) 付けずに、絵を画面の上に貼り付けて動かなくする（PR #8 の判断が要る点 A の推奨）。
- 推奨: (b) で 70vh 。90vh だと絵の下に何も入らず、選択肢があることに気づけない。
  70vh なら画面の3割が残り、選択肢の1つ目が必ず視野に入る。
  (c) とは競合しないので、両方入れることもできる。先に (b) を入れておくと、
  (c) を試すときの絵の高さが決まっていて実装が短くなる。
- 答え方: 「絵の高さ: a」「絵の高さ: b 70vh」「絵の高さ: c」

### C. 絵の後ろと縁を、どう作るか

- 決めること: A で (b) を選ぶと、絵の入らなかった部分に地が出る。その色と、
  絵と枠のあいだの扱い。
- 選択肢:
  - (a) いまの `bg-sunken` のまま。
  - (b) 紙の地（2026-08-31 の調査の推奨は #fdf8f6）と同じ色にして、
    絵の輪郭は 1px の線で示す。絵の白い地と画面の紙の地の差がそのまま境目になる。
  - (c) 白にする。白い地の絵は境目が消えるので、線が必須になる。
- 推奨: (b)。絵の多くは白い地を持つので、後ろを紙色にすると絵の実際の縁が見える。
  線を1本入れるのは、白でない地の絵（透過や黒い地）でも縁が分かるようにするため。
  あわせて、絵と線のあいだに 4px ほどの余白を置くと、端まで描かれた絵の線と
  枠の線が重ならない（事例8）。
- 答え方: 「絵の地: a」「絵の地: b」「絵の地: c」
