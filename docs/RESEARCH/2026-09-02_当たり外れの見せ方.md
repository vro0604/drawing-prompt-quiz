# 2026-09-02 当たり外れを、色以外の何で見せているか

今日調べたのは、選択式の問題で「合っていた」「外れた」「惜しい」を、実在の部品や
実在のゲームがどう見せているか。色のほかに何の手がかりを重ねているか、
外れた側をどう扱っているか、結果を音声読み上げにどう伝えているか。

これを選んだ理由は、2026-08-31 の調査（未 merge の PR #6）が末尾で
「当たり外れの色を主色と分けるか」を判断待ちとして出したものの、色の値までしか
調べていないため。このサービスは絵からお題を当てる仕組みそのものなので、
当たり外れの見せ方は画面の飾りではなく機能の中心にある。

## 事例

### 1. WCAG 2.2 の達成基準 1.4.1「色の使用」の解説

- 出所: https://github.com/w3c/wcag （読んだ版 2cde22e 、2026-08-28。
  ファイルは understanding/20/use-of-color.html）
- 何をしているか: 色の違いだけで意味を伝えてはいけない、という基準の意図を説明している。
  色の違いに加えて明るさの差が十分（比 3:1 以上）にあれば、それ自体が
  「もう1つの視覚的な手がかり」として数えられる、という緩和も書かれている。
- ただし、そのすぐあとに例外が書いてある。利用者が特定の色を正しく見分けられることに
  依存する場合は、明るさの差がいくらあっても追加の手がかりが要る、として、
  その例に「枠が緑なら妥当、赤なら不当」を挙げている。
- なぜそうしていると思われるか: 「緑と赤」は、色の見え方に個人差が出る組み合わせの
  代表で、しかも意味が色そのものに埋め込まれている。明るさが違っても、
  どちらが正でどちらが誤かは色を見分けないと決まらない。推測ではなく、
  解説文が名指しでこの例を挙げている。
- このプロジェクトに当てはめるなら: 正解を緑、外れを赤にするなら、色に加えて
  記号（丸と罰など）か文字（「当たり」「外れ」）を必ず併せる。これは好みではなく、
  今日読んだ中で唯一、明文で要求されている条件だった。
- 当てはめない方がよい理由: 無し。ただしこの基準は「色だけに頼るな」であって、
  「色を使うな」ではない。解説文自身が、色分けを妨げるものではないと断っている。

### 2. GOV.UK Frontend のエラーメッセージ部品

- 出所: https://github.com/alphagov/govuk-frontend （読んだ版 a3b356a 、2026-09-01。
  ファイルは packages/govuk-frontend/src/govuk/components/error-message/ の
  template.njk と _mixin.scss）
- 何をしているか: 誤りの知らせを、3つの手がかりの重ねで作っている。色（役目の名前で
  error を指す）、太字、そして本文の前に置いた読み上げ専用の語「Error:」。
  この語は画面には出ず（govuk-visually-hidden）、読み上げにだけ入る。
  差し替えできる引数になっていて、既定値が "Error" 。
- なぜそうしていると思われるか: 色と太字は目で見る人向け、隠した語は読み上げで聞く人向けで、
  同じ意味を2つの経路に別々に流している。片方だけでは足りないという判断が形になっている。
- このプロジェクトに当てはめるなら: 外れの表示に、画面には出さない「不正解:」という語を
  文頭に置く。見た目は今のままで、読み上げでだけ結果が先に伝わる。
- 当てはめない方がよい理由: 無し。ただし日本語の読み上げでは、隠し語と本文が続けて
  読まれたときの区切りを確かめる必要がある。

### 3. GOV.UK Frontend の知らせの帯と、ラベルの色の組み方

- 出所: 同上（a3b356a 、2026-09-01。ファイルは components/notification-banner/ の
  template.njk と _mixin.scss 、components/tag/_mixin.scss 、
  settings/_colours-palette--internal.scss）
- 何をしているか: 知らせの帯は、成功のときだけ扱いを変える。role に "alert" を入れ
  （読み上げが今の作業を中断してでも先に読む指定）、見出しの既定値を "Success" にし、
  色を成功の役目に切り替える。成功でないときは role が "region" で、割り込まない。
  ソースの注釈に「支援技術の利用者に対して情報を優先させるため」と理由が書いてある。
- 同じリポジトリのラベル部品（tag）は、色の組を人が選ばず式で作っている。
  文字はその色の shade-50（最も濃い段）、地は tint-80（最も薄い段）。
  たとえば緑なら文字 #083d29 と地 #cfe4dc で、計算すると比は 9.23 。赤なら 9.01 。
- なぜそうしていると思われるか: 結果は「今この瞬間に伝えるべきこと」なので割り込ませ、
  ラベルは一覧に並ぶ飾りなので割り込ませない、という切り分けだと思われる。推測。
- このプロジェクトに当てはめるなら: 答え合わせの結果を出す枠に role="alert" を付ける。
  当たり外れのラベルを作るなら、濃い文字と薄い地の組にする。この組み方なら、
  紙の地の上でも文字は 9:1 前後を保てる。
- 当てはめない方がよい理由: 割り込みの指定は、連続して何度も出すと読み上げが
  そのたび中断されて邪魔になる。1問ごとに出すなら、まとめて1回にする方がよい。

### 4. デジタル庁デザインシステムのデザイントークン

- 出所: https://github.com/digital-go-jp/design-tokens （読んだ版 cde7dfe 、2026-05-28。
  ファイルは figma/tokens.json）
- 何をしているか: 意味を持つ色（Semantic）を、成功・エラー・注意の3つに絞り、
  各2段だけ持たせている。成功は緑の 600 と 800 、エラーは赤の 800 と 900 。
  素の色は10系統13段あるのに、意味に結びつける段は2つに絞っている。
- なぜそうしていると思われるか: 2段の意味は、計算すると分かる。白地に対して
  成功の 600（#259d63）は 3.45 、800（#197a4b）は 5.35 。文字に要る 4.5 と
  文字でない部分に要る 3.0 の、それぞれに1段ずつ当ててあると思われる。
- このプロジェクトに当てはめるなら: 当たり外れの色を1つずつではなく2段で持つ。
  枠線や下線には薄い段、文字には濃い段を使う。3段目は作らない。
- 当てはめない方がよい理由: 無し。ただし PR #6 が同じファイルを読んで同じ値を
  引いているので、こちらの報告では二度書きにならないよう数値の表だけ後ろにまとめた。

### 5. H5P の多肢選択（Multi Choice）

- 出所: https://github.com/h5p/h5p-multi-choice （読んだ版 f2cf935 、2026-08-31。
  ファイルは js/multichoice.js 、css/multichoice.css 、semantics.json）
- 何をしているか: 答え合わせのとき、選んだ選択肢に印を差し込む。印は書体の記号
  （正解が \e903 、外れが \e902）で、形が違う。色は正解用と外れ用の別々の変数。
  さらに、その印の要素に読み上げ用の文字（既定は "Correct answer" / "Wrong answer"）を
  aria-label として付ける。semantics.json の説明欄に「読み上げ用の文字」と明記され、
  画面には出さないと書いてある。
- 正解の開示は、これとは別の印を使う。「選ぶべきだった（Should have been checked）」と
  「選ぶべきでなかった（Should not have been checked）」の2種類で、色は本文と同じ色。
  つまり、自分の正誤と、正解がどれかは、別々の印で示している。
- なぜそうしていると思われるか: 形・色・読み上げ用の文字の3経路に同じ意味を流していて、
  事例1が求めていることを部品の側で満たしている。また「自分は外した」と
  「正解はこれ」を分けたのは、両方を同じ赤で塗ると読み取れなくなるためだと思われる。推測。
- このプロジェクトに当てはめるなら: 結果の画面で、選んだお題に正誤の印を付け、
  正解のお題には別の印を付ける。同じ色で二重に塗らない。
- 当てはめない方がよい理由: 記号を書体（アイコンフォント）で持つやり方は、
  書体の読み込みが失敗すると意味ごと消える。文字か図形で持つほうが安全。

### 6. scribble.rs（絵を見て言葉を当てる対戦ゲーム）

- 出所: https://github.com/scribble-rs/scribble.rs （読んだ版 0003127 、2026-05-31。
  ファイルは internal/frontend/lobby.js 、internal/frontend/resources/lobby.css 、
  internal/translations/en_us.go）
- 何をしているか: このプロジェクトといちばん近い形のゲーム。当てる側の発言に対して、
  3つの状態を別々に扱う。自分が当てた（緑・太字、「You have correctly guessed the word.」）、
  他の人が当てた（黄・太字）、惜しい（青緑・太字、「'（入力した語）' is very close.」と
  入力そのものを引用して返す）。正解のときは音（plop.wav）も鳴らす。
- 外れた発言には、専用の扱いが1つも無い。ふつうの発言としてそのまま並ぶだけで、
  色も印も付かない。目立たせるのは当たりと惜しいだけ、という作りになっている。
- なぜそうしていると思われるか: 外れを毎回赤で塗ると画面が赤だらけになり、
  当たりが埋もれる。当たりが珍しいから価値がある、という遊びの性質に合わせたのだと思われる。推測。
- このプロジェクトに当てはめるなら: 「惜しい」の状態を作る価値がある。
  お題は選択式なので、同じ分類の別のお題を選んだときに「近い」と返せる。
  外れは赤で塗らず、そのまま残す。
- 当てはめない方がよい理由: 色の濃さは真似できない。計算すると、緑 #26bb26 は
  白地で 2.56 、他の人が当てた黄 #e7c620 は 1.68 しかない。文字に要る 4.5 に遠く届かず、
  この配色をそのまま持ってくると読めない人が出る。

### 7. Bootstrap の入力欄の検証表示

- 出所: https://github.com/twbs/bootstrap （読んだ版 12cb8b9 、2026-09-01。
  ファイルは scss/_variables.scss の form-feedback 節、scss/forms/_validation.scss 、
  site/src/content/docs/forms/validation.mdx）
- 何をしているか: 妥当と不当を、色（成功色と危険色）、枠線、それに入力欄の中へ
  埋め込む小さな図で示す。図は共通の形ではなく、妥当がチェックの線、
  不当が丸の中に感嘆符で、形が違う。加えて、欄の下に文（feedback）を置く枠がある。
- 同じリポジトリの説明文の冒頭に、警告が置いてある。独自の検証表示は支援技術に
  伝わらないので、伝わるまでは標準の検証か、サーバー側での表示を使うよう勧めている。
- なぜそうしていると思われるか: 色と図と文の3つを載せてもなお、それが読み上げに
  出ていなければ足りない、と作った側自身が認めている例。事例2と5が隠し文字を
  わざわざ入れている理由が、裏側から確かめられる。
- このプロジェクトに当てはめるなら: 正誤の印を図形で描くなら、正解と外れで形を変える。
  そのうえで、図形だけで済ませず、読み上げに出る文字を必ず添える。
- 当てはめない方がよい理由: 入力欄の検証と、クイズの答え合わせは目的が違う。
  借りるのは「形を変える」「文を添える」の2点だけでよい。

## 自分で計算した表

事例に出てきた色を、白地と紙の地に対して計算した。紙の地は PR #6 が推している
#fdf8f6 を使った。文字として使うには 4.5 以上、文字でない部分だけなら 3.0 以上が要る。

| 色 | 値 | 白 #ffffff | 紙 #fdf8f6 |
|---|---|---|---|
| デジタル庁 Green.600 | #259d63 | 3.45 | 3.28 |
| デジタル庁 Green.800 | #197a4b | 5.35 | 5.08 |
| デジタル庁 Red.800 | #ec0000 | 4.60 | 4.37 |
| デジタル庁 Red.900 | #ce0000 | 5.79 | 5.50 |
| GOV.UK 緑 primary | #0f7a52 | 5.35 | 5.08 |
| GOV.UK 赤 primary | #ca3535 | 5.16 | 4.90 |
| GOV.UK 緑 shade-50 | #083d29 | 12.28 | 11.66 |
| GOV.UK 赤 shade-50 | #651b1b | 12.17 | 11.55 |
| scribble 正解（自分） | #26bb26 | 2.56 | 2.43 |
| scribble 正解（他人） | #e7c620 | 1.68 | 1.60 |
| scribble 惜しい | #19a6a6 | 2.98 | 2.83 |

読み取れること。

- 赤の #ec0000 は、白地では 4.60 で通るのに紙の地では 4.37 で割る。
  地を紙色にする決定は、当たり外れの色の選び直しを連れてくる。
- ゲームの3色は、どれも文字の基準に届かない。楽しさを優先した配色で、
  そのまま借りると読めない。
- GOV.UK の緑と赤は、白でも紙でも 4.9 以上あり、どちらの地でも文字に使える。
  この2色は地を変えても選び直さなくてよい。
- ラベルの形（濃い文字＋薄い地）にすると 9:1 前後まで上がる。ただし薄い地そのものは
  紙に対して 1.26 と 1.28 しかなく、地としての境目は見えない。枠線か文字で形を示す必要がある。

## 判断が要る点

### A. 当たり外れを、色のほかに何で示すか

- 決めること: 正解・不正解の表示に、色以外の手がかりを何本入れるか。
- 選択肢:
  (a) 色だけ。
  (b) 色＋形（正解と外れで違う図形）。
  (c) 色＋形＋読み上げ用の隠し文字。
- 推奨: (c)。事例1が「緑なら正、赤なら誤」を名指しで、明るさの差では足りない例に
  挙げている。形は事例5と7が両方とも入れている。隠し文字は事例2と5の作り方をそのまま使える。
  追加で要るのは各表示に一言ぶんの文字だけで、見た目は変わらない。
- 答え方: 「A: a」「A: b」「A: c」

### B. 外れをどう扱うか

- 決めること: 外れた選択肢を、赤などで目立たせるか、印だけにするか、何もしないか。
- 選択肢:
  (a) 外れも赤で塗る（事例5・7の型）。
  (b) 外れには印だけ付け、色は本文と同じにする。正解の側だけ色を持たせる。
  (c) 外れには何も付けない（事例6の型）。正解だけを見せる。
- 推奨: (b)。このサービスは絵が主役で、外れが並ぶ画面が赤くなると絵の色と競合する。
  一方 (c) は、選択式で自分がどれを選んだか分からなくなる。印だけ残せば、
  自分の選択は追えて、画面は静かなままになる。
- 答え方: 「B: a」「B: b」「B: c」

### C.「惜しい」の状態を作るか

- 決めること: 当たりと外れの2つだけにするか、あいだに「惜しい」を置くか。
- 選択肢:
  (a) 当たりと外れの2つだけ。
  (b) 「惜しい」を足す。同じ分類の別のお題を選んだときに出す。
  (c) 「惜しい」を足し、得点にも反映する。
- 推奨: (b)。このサービスは上手さではなく伝わりやすさを測るので、
  「近いところまでは伝わった」は測りたいものそのものに近い。ただし (c) まで進めると
  得点の意味が変わるので、まずは表示だけにする。分類は docs/tags-master.md にある
  ものを使えるかどうかを、実装の前に確かめること。
- 答え方: 「C: a」「C: b」「C: c」
