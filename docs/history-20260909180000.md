## 2. 次の工程でやること（読み取りと使い捨ての DB だけ）

1. 本番の履歴を読み取りで取り直す（`supabase_migrations.schema_migrations` の全行。version・name・statements）
2. 使い捨ての PostgreSQL 17.6 を本番と同じ UTF8 / ICU / 既定の権限で立てる
   （`embedded-postgres`。initdb の指定は memory の pg17-local-needs-prod-locale と同じ）
3. 本番の履歴と同じ順で67本を当て、履歴表に**本番の行をそのまま**写す（20260909180000 の行も、食い違ったまま写す）
4. 修復の候補を1つずつ当てて、次を記録する
   - 当てる前と後の、20260909180000 の行（version・name・statements の数と md5）
   - スキーマ（関数・表・索引・制約・権限）が1文字も変わらないこと
   - 67本の他の行が変わらないこと
   - `supabase migration list` / `db push --dry-run` の出力が変わらないこと
   - 取り消す手順（元の行へ戻す）が通ること
5. 候補（どれが本当に何をするかは**未検証**。この工程で確かめる）
   - `supabase migration repair 20260909180000 --status reverted` のあと `--status applied`
   - 履歴表の1行だけを、手元のファイルの name と statements で書き換える SQL（1トランザクション）
   - 何もしない（食い違いを記録として残す）
6. 結果を表にして、本番で行うかを判断してもらう
